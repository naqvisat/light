AWS SQS & SNS - Complete SAA-C03 Cheat Sheet

A simple text reader version of the SQS and SNS cheat sheet, covering queueing, pub/sub, DLQs, FIFO, fan-out, filtering, and common exam architectures.

1. Messaging Overview - Why Decouple?

  • Tightly coupled systems fail and scale together. Loosely coupled systems decouple producers and consumers with queues or topics.
  • Queue model (SQS): One producer sends a message, one consumer processes it. Best for work distribution and task processing.
  • Pub/Sub model (SNS): One publisher sends a message, many subscribers each receive a copy. Best for notifications and event broadcasting.
  • Common architecture: SNS plus SQS fan-out. Producer sends once to SNS and multiple SQS queues receive copies.

2. Amazon SQS - Fundamentals

  • Fully managed serverless message queuing service with automatic scaling.
  • Unlimited throughput: No limit on messages per second or messages in a queue.
  • Retention: Default four days, configurable from one minute to 14 days.
  • Message size: Up to 256 KB. Use the Extended Client Library with S3 for larger payloads.
  • Standard queue behavior: At-least-once delivery and best-effort ordering.
  • Messages are stored durably across multiple AZs.

3. SQS - Producing & Consuming Messages

  • Producers send messages with the SendMessage API, optionally including attributes.
  • Consumers poll, receive, process, and explicitly delete messages.
  • Short Polling: Returns immediately, can waste calls with empty responses.
  • Long Polling: Waits up to 20 seconds and is preferred because it reduces empty responses and cost.
  • Batch operations: Send, receive, or delete up to 10 messages per API call.
  • Scale out consumers horizontally to process more messages in parallel.

4. SQS - Visibility Timeout

  • After a consumer receives a message, it becomes invisible to other consumers for the visibility timeout period.
  • Default: 30 seconds. Configurable from 0 seconds to 12 hours.
  • If the consumer deletes the message before timeout, processing succeeds and the message is removed.
  • If the consumer fails or takes too long, the message becomes visible again for retry.
  • ChangeMessageVisibility: Extend the timeout for long-running tasks.

5. SQS - Dead Letter Queue (DLQ)

  • A separate queue for messages that fail processing too many times.
  • MaxReceiveCount: Number of failed receives before the message moves to the DLQ.
  • DLQ must be the same queue type as the source queue.
  • Use for debugging, isolating bad messages, and alerting on failures.
  • DLQ Redrive: Move messages back for reprocessing after fixing the issue.

6. SQS - Delay Queues & Message Timers

  • Delay Queue: Queue-level delay before messages first become visible, up to 15 minutes.
  • Message Timer: Per-message delay, also up to 15 minutes, not available on FIFO queues.
  • Use for delayed processing, cooldowns, and throttling downstream systems.
  • Exam distinction: Delay queue is before first delivery. Visibility timeout is after delivery.

7. SQS - FIFO Queue

  • Guarantees ordered processing and exactly-once delivery behavior.
  • Queue name must end with .fifo.
  • Message Group ID: Defines the ordering lane. Same group means in-order one-at-a-time processing.
  • Message Deduplication ID: Prevents duplicate sends within a five-minute window.
  • Supports up to 300 messages per second, or more with batching and High Throughput FIFO.

8. SQS - Security

  • Encryption in transit uses HTTPS by default.
  • Encryption at rest can use SSE-KMS or SSE-SQS.
  • IAM policies: Control API-level access.
  • SQS Queue Policy: Resource-based policy used for cross-account access and for services like S3 or SNS sending to the queue.
  • VPC Endpoint: Use an Interface VPC Endpoint for private subnet access without the internet.

9. SQS - Scaling Consumers with ASG

  • Common pattern: SQS queue with EC2 consumers in an Auto Scaling Group.
  • Scaling metric: ApproximateNumberOfMessagesVisible.
  • Use CloudWatch alarms and ASG scaling policies to add consumers when queue depth rises.
  • Custom metric such as messages per instance is useful for more precise scaling.

10. SQS - Temporary Queues & Request-Response Pattern

  • Temporary Queue Client enables lightweight request-response patterns with virtual queues.
  • Producer sends a request with a reply queue reference, consumer processes it, then sends the response back.
  • Useful for RPC-style communication over asynchronous SQS.

11. Amazon SNS - Fundamentals

  • Fully managed serverless pub/sub messaging service.
  • A publisher sends a message to an SNS topic and all subscribers receive a copy.
  • Topics and subscriptions scale massively with soft account limits.
  • Message size is also capped at 256 KB, with Extended Client Library patterns available for larger payloads.

12. SNS - Publishers & Subscribers

  • Publishers include applications and many AWS services such as S3, CloudWatch, ASG, RDS, and CodePipeline.
  • Subscribers: SQS, Lambda, HTTP/HTTPS, email, SMS, Kinesis Data Firehose, and mobile push notifications.
  • Exam pattern: If the question says one message must notify multiple systems, think SNS topic.

13. SNS - Fan-Out Pattern (SNS + SQS)

  • One SNS topic fans out one published message to multiple SQS queues.
  • This decouples the producer from the consumers and lets you add new subscribers without changing producer code.
  • Cross-Region SQS subscriptions are supported.
  • Queue policies must allow the SNS topic to send messages.
  • Common use case: one event triggers multiple independent processing pipelines.

14. SNS - Message Filtering

  • By default, every subscriber receives every message. Filter policies let each subscription receive only relevant messages.
  • Filters can use message attributes or the message body.
  • Supports exact match, prefix, numeric conditions, exists, and combined logic.
  • Use when different consumers need different subsets from the same topic.

15. SNS - FIFO Topics

  • Guarantees strict ordering and exactly-once delivery semantics for FIFO subscribers.
  • Topic name must end with .fifo.
  • Only SQS FIFO queues can subscribe to an SNS FIFO topic.
  • Uses Message Group ID and Deduplication ID concepts similar to SQS FIFO.

16. SNS - Security

  • HTTPS is used for encryption in transit.
  • SSE-KMS encrypts messages at rest.
  • IAM policies: Control who can publish or subscribe.
  • SNS Topic Policy: Resource-based policy for cross-account or service publishing and subscribing.

17. SNS - Message Delivery & Retry

  • SNS retries SQS and Lambda deliveries immediately, then with exponential backoff for up to 23 days.
  • HTTP/HTTPS retry behavior is configurable.
  • DLQs can be configured for subscriptions to capture undeliverable messages.
  • Without a DLQ, failed messages are dropped after retries are exhausted.

19. SQS + SNS + Lambda - Common Architectures

  • Fan-out processing: one event to multiple queues and Lambda subscribers.
  • Decoupled microservices: API producer to SQS, then Lambda or EC2 consumers.
  • Buffered writes: SQS between incoming traffic and DynamoDB writes.
  • Cross-account messaging using topic policies and queue policies.
  • Ordered fan-out using SNS FIFO topics and SQS FIFO queues.

20. Amazon EventBridge (vs SNS)

  • EventBridge supports advanced filtering, schema registry, archive and replay, SaaS integrations, and multiple event buses.
  • SNS is better for simple high-volume fan-out plus SMS, email, and push notifications.
  • Exam decision: Simple fan-out means SNS. Complex routing or replay means EventBridge.

21. Amazon MQ

  • Managed broker for ActiveMQ and RabbitMQ using standard messaging protocols.
  • Not serverless. Runs on provisioned infrastructure.
  • Use for migrating existing on-prem messaging apps without rewriting them.
  • For new cloud-native architectures, prefer SQS plus SNS.

22. Kinesis vs SQS - When to Choose Which

  • Kinesis Data Streams: Real-time streaming with ordered data per shard, multiple consumers, and replay.
  • SQS: One-time message consumption for decoupling and buffering.
  • Use Kinesis for streaming analytics and multiple readers. Use SQS for asynchronous task distribution.

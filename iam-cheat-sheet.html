AWS IAM - Complete SAA-C03 Cheat Sheet

A simple text reader version of the full IAM cheat sheet, preserving the original section structure and decision matrix.

1. IAM Fundamentals

  • IAM is a global service - not Region-specific. Users, groups, roles, and policies are available across all Regions.
  • Root account is created when you first set up an AWS account. It has unrestricted access to everything. Never use root for daily tasks. Enable MFA on root immediately.
  • Tasks that ONLY root can do: close the account, change the account name/email/root password, change the AWS support plan, restore IAM permissions, register as a seller in the Reserved Instance Marketplace, configure S3 bucket policy with MFA Delete, edit/delete an S3 bucket policy that includes an invalid VPC ID or endpoint ID.
  • IAM provides authentication (who are you?) and authorization (what can you do?).
  • IAM is free - no charge for users, groups, roles, or policies.

2. IAM Users, Groups & Accounts

  • IAM User: An identity with long-term credentials (password for console, access keys for CLI/API). Represents a person or application.
  • IAM Group: A collection of IAM users. You attach policies to groups, and all users in the group inherit those permissions. A user can belong to multiple groups (up to 10). Groups cannot be nested (no groups inside groups). Groups are not identities - you cannot reference a group in a resource-based policy's Principal field.
  • Best practice: Never attach policies directly to users - attach them to groups instead. Even if a "group" has one member, use a group.
  • AWS account limits (defaults): 5,000 IAM users per account, 300 groups, 1,000 IAM roles. If you need more than 5,000 identities, use IAM Identity Center (SSO) with an external IdP.

3. IAM Policies

  • Policy types (in order of exam importance):
    • Identity-based policies: Attached to users, groups, or roles. Define what that identity is allowed or denied to do.
    • Resource-based policies: Attached directly to a resource (S3 bucket policy, SQS queue policy, KMS key policy, Lambda function policy). Define who can access that resource and what they can do. Contain a Principal field.
    • Permissions boundaries: Set the maximum permissions an identity CAN have. Does not grant permissions on its own - it limits what identity-based policies can grant. Used for delegation.
    • Service Control Policies (SCPs): Applied at the AWS Organizations level to OUs or accounts. Restrict what the entire account, including root, can do. Do not grant permissions. Do not affect the management account.
    • Session policies: Passed when assuming a role or federating. Limit the permissions for that session only.
  • Policy evaluation logic: Explicit Deny always wins, then SCPs, then Permissions Boundaries, then identity-based and resource-based policies. If nothing explicitly allows, the default is implicit deny.
  • AWS Managed vs Customer Managed vs Inline Policies:
    • AWS Managed: Created and maintained by AWS. General-purpose. Cannot be edited.
    • Customer Managed: Created by you. Reusable across multiple identities. Best practice for custom needs.
    • Inline: Embedded directly in a single user, group, or role. Not reusable. Use only for strict 1-to-1 relationships where the policy must be deleted when the identity is deleted.

4. IAM Policy Structure (JSON)

  • Every policy is a JSON document with: Version, Statement (array of individual permission blocks).
  • Each Statement contains:
    • Effect: Allow or Deny.
    • Action: The API calls being allowed or denied, such as s3:GetObject or ec2:StartInstances. Supports wildcards.
    • Resource: The ARN or ARNs the statement applies to. Use * for all resources or specify exact ARNs.
    • Condition (optional): When the statement applies, such as only if MFA is present or only from a specific IP range.
    • Principal (resource-based policies only): Who is allowed or denied.
  • NotAction / NotResource: The inverse - everything except these actions or resources. Exam trap: Allow NotAction: iam:* means allow everything except IAM actions. It does not explicitly deny IAM actions.

5. IAM Policy Conditions - Exam Favorites

  • aws:SourceIp: Restrict API calls to specific IP ranges.
  • aws:MultiFactorAuthPresent: Require MFA for sensitive actions.
  • aws:RequestedRegion: Restrict resource creation to specific Regions.
  • aws:PrincipalTag / aws:ResourceTag: Attribute-based access control based on user or resource tags.
  • s3:x-amz-server-side-encryption: Enforce encryption on S3 uploads.
  • aws:SecureTransport: Deny requests that are not over HTTPS.
  • ec2:ResourceTag: Restrict EC2 actions based on instance tags.
  • StringEquals vs StringLike: StringEquals is exact match. StringLike supports wildcards.

6. IAM Roles

  • IAM Role: An identity with temporary credentials. No long-term password or access keys. Anyone or anything that assumes the role gets temporary security credentials via STS.
  • Use cases: EC2 instances accessing AWS services, Lambda functions, cross-account access, federated users, AWS services acting on your behalf.
  • Trust Policy: A resource-based policy on the role that defines who can assume the role.
  • Permission Policy: Defines what the role can do once assumed.
  • EC2 Instance Profile: A container for an IAM role attached to an EC2 instance. The instance can call AWS APIs without embedding access keys. Only one role per instance.
  • Cross-account role assumption: Account A creates a role with a trust policy allowing Account B. A user in Account B calls sts:AssumeRole to get temporary credentials to act in Account A.
  • Service-Linked Roles: Pre-defined roles that allow AWS services to perform actions on your behalf. Created and managed by the service.

7. AWS STS (Security Token Service)

  • STS provides temporary credentials: Access Key ID, Secret Access Key, and a Session Token. These expire.
  • Key APIs:
    • AssumeRole: Assume a role within your account or cross-account. Most common on the exam.
    • AssumeRoleWithSAML: For users authenticated via a SAML 2.0 identity provider.
    • AssumeRoleWithWebIdentity: For users authenticated via a web identity provider. AWS recommends Cognito instead of calling this directly.
    • GetSessionToken: For MFA-protected API access.
    • GetCallerIdentity: Returns the IAM user or role ARN and account ID.
  • Revoking temporary credentials: You cannot invalidate a specific set of temp credentials. Instead, update the role's policy to deny sessions issued before a certain time using aws:TokenIssueTime.

8. IAM Identity Center (formerly AWS SSO)

  • One centralized login for all AWS accounts in your Organization and SAML 2.0 compatible business applications.
  • Supports built-in identity store or integration with external identity providers such as Active Directory, Okta, or Azure AD.
  • Uses Permission Sets - a collection of policies that define what a user can do in a specific account. Assigned to users or groups for specific accounts.
  • Supports ABAC (attribute-based access control) based on user attributes from the identity store.
  • Exam pattern: Centralize access management across multiple AWS accounts - use IAM Identity Center.

9. Federation - External Identity Providers

  • SAML 2.0 Federation: For corporate environments with Active Directory or any SAML 2.0-compatible IdP. Users authenticate with the IdP, get a SAML assertion, and exchange it for temporary AWS credentials via STS.
  • Web Identity Federation: For mobile or web app users authenticating via Google, Facebook, or Amazon. AWS recommends using Amazon Cognito as the intermediary.
  • Amazon Cognito:
    • User Pools: User directory for sign-up and sign-in. Handles authentication and issues JWT tokens.
    • Identity Pools: Provides temporary AWS credentials to access AWS resources directly. Supports unauthenticated guest access.
    • Exam pattern: Mobile app users need to access S3 directly - use Cognito User Pool plus Identity Pool.
  • Custom Identity Broker: If your IdP is not SAML 2.0 compatible, build a custom broker that authenticates users against your IdP and calls STS.
  • Active Directory integration options:
    • AWS Managed Microsoft AD: Full AD in AWS. Two-way trust with on-prem AD.
    • AD Connector: Proxy to redirect requests to on-prem AD.
    • Simple AD: Standalone managed directory powered by Samba.

10. Cross-Account Access Patterns

  • IAM Roles (AssumeRole): Account A creates a role trusting Account B. Users in B assume the role. Best for programmatic cross-account access, temporary access, and auditable access.
  • Resource-Based Policies: The resource in Account A grants access to a principal in Account B directly. No role assumption needed.
  • Key difference: With role assumption, you give up your original permissions and get only the role's permissions. With resource-based policies, you keep your own permissions and add the resource's granted permissions.
  • AWS Organizations SCPs: Central guardrails across accounts. Even if an account's IAM policy allows an action, the SCP can block it.
  • AWS RAM (Resource Access Manager): Share specific resources with other accounts or your entire Organization without cross-account roles.

11. IAM Access Analyzer

  • Analyzes resource policies to identify resources shared with external entities.
  • Zone of trust means your AWS account or Organization. Anything outside is flagged as a finding.
  • Supports S3 buckets, IAM roles, KMS keys, Lambda functions, SQS queues, and Secrets Manager secrets.
  • Policy Generation: Monitors CloudTrail logs to generate a least-privilege policy based on actual API activity over a period of up to 90 days.
  • Policy Validation: Checks your policies for grammar errors, best practice warnings, and security findings before deployment.

12. IAM Best Practices & Security Tools

  • Enable MFA for all users, especially root.
  • Use roles for EC2, Lambda, and services - never embed access keys.
  • Apply least privilege - start with minimum permissions and add as needed.
  • Use IAM Access Analyzer to find externally shared resources and generate least-privilege policies.
  • Rotate access keys regularly. Use IAM Credential Reports to audit all users' credential status.
  • IAM Credential Report (account-level): CSV file listing all users and the status of their credentials.
  • IAM Access Advisor (user/role-level): Shows which services a user or role has accessed and when they last accessed them.
  • AWS CloudTrail: Logs every API call. Essential for IAM auditing.

13. Encryption & IAM - KMS Key Policies

  • Every KMS key must have a key policy. If the key policy does not explicitly allow access, IAM policies alone cannot grant access to the key.
  • Default key policy: Allows the root user of the account full access to the key, which then enables IAM policies to grant access to the key to other users or roles.
  • Cross-account KMS access: The key policy must allow the external account, and the external account must have an IAM policy allowing KMS actions.
  • Grants: Lightweight, temporary permissions to use a KMS key. Useful for AWS services that need to use a key on your behalf.

14. AWS Organizations & SCPs

  • AWS Organizations: Centrally manage multiple AWS accounts. Features include consolidated billing, SCPs, tag policies, and backup policies.
  • Organization structure: Management account to Organization Units to member accounts. OUs can be nested.
  • SCPs (Service Control Policies): JSON policies that define the maximum available permissions for member accounts. They do not apply to the management account and do not grant permissions.
  • SCP inheritance: SCPs are inherited from parent OUs. Effective permissions are the intersection of all inherited SCPs.
  • SCP strategies:
    • Deny-list: FullAWSAccess everywhere, then explicit deny SCPs for specific actions.
    • Allow-list: Remove FullAWSAccess, then only explicitly allow specific services.
  • Exam pattern: Prevent any account in the organization from disabling GuardDuty, leaving the org, or creating resources outside approved Regions - use an SCP with explicit Deny.

15. Resource-Based Policies - Deep Dive

  • Not all AWS services support resource-based policies. Key services that do include S3, SQS, SNS, Lambda, KMS, API Gateway, Secrets Manager, ECR, EventBridge, and Backup vaults.
  • S3 Bucket Policies: Most common on the exam. Can grant cross-account access, enforce encryption, enforce HTTPS, restrict by VPC endpoint, or restrict by IP range.
  • Lambda Resource-Based Policy: Controls who or what can invoke the function.
  • SQS Queue Policy: Controls who can send messages to or receive messages from the queue. Required for cross-account access and for allowing SNS or S3 to send messages to the queue.

AWS VPC - Complete SAA-C03 Cheat Sheet

A simple text reader version of the full VPC cheat sheet, preserving the original section structure and decision matrix.

1. VPC Fundamentals

  • VPC is Region-wide and spans all AZs in that Region. Subnets are AZ-specific - one subnet lives in exactly one AZ.
  • Default VPC: Every Region comes with a default VPC (CIDR 172.31.0.0/16) with a default subnet in each AZ, an attached IGW, and a default NACL that allows all traffic. Default subnets are public (they auto-assign public IPs).
  • VPC CIDR range: minimum /28 (16 IPs), maximum /16 (65,536 IPs).
  • You can add secondary CIDR blocks to an existing VPC (up to 5, extendable to 50), but they must not overlap with the primary CIDR or any peered VPC CIDRs.
  • AWS reserves 5 IPs in every subnet: .0 (network address), .1 (VPC router), .2 (DNS server), .3 (reserved for future use), .255 (broadcast). So a /24 subnet gives you 251 usable IPs, not 256.
  • Tenancy: Default (shared hardware) or Dedicated (single-tenant hardware). Setting a VPC to dedicated forces all instances in it to launch on dedicated hardware - this cannot be changed back to default.

2. Routing

  • Every VPC has a main route table. Every subnet must be associated with exactly one route table. If you don't explicitly associate one, the subnet uses the main route table.
  • IGW and Route Tables are Region-wide resources. Recommended practice is to create a Route Table specific to each AZ for better isolation and high availability.
  • Most specific route wins. If your table has 0.0.0.0/0 -> IGW and 10.0.0.0/16 -> local, traffic to 10.0.0.5 goes local because /16 is more specific than /0.
  • The "local" route (for intra-VPC traffic) is always present and cannot be removed or overridden.

3. Security - NACLs vs Security Groups

  • NACL (Network ACL): Subnet-level, stateless, supports both Allow and Deny rules. Rules are evaluated in number order (lowest first) - first match wins, remaining rules are skipped. The default NACL allows all inbound and outbound. A custom NACL denies everything by default until you add rules.
  • Security Group: Instance-level (ENI-level), stateful (return traffic is automatically allowed), supports only Allow rules (no explicit Deny). Default SG allows all outbound and allows inbound only from the same SG.
  • Because NACLs are stateless, return traffic must be explicitly allowed. If you allow inbound TCP 443, you must also allow outbound on ephemeral ports (1024-65535) for responses to flow back. This is the #1 NACL troubleshooting trap on the exam.
  • Security Groups can reference other Security Groups as sources/destinations - not just IP ranges. This is a powerful pattern for multi-tier architectures (e.g., "allow inbound on port 3306 only from the web-tier SG").
  • Security Groups are stateful per connection: if you allow inbound on port 80, the response is automatically allowed. But if you initiate a new outbound connection, you need an outbound rule for it.
  • Layered security model: Use Security Groups as the primary defense (allow-list model) and NACLs as a secondary subnet-wide guardrail (e.g., explicitly block a known malicious IP range across the entire subnet).

4. VPC Flow Logs

  • Flow Logs capture IP traffic metadata (not packet contents) - source/dest IPs, ports, protocol, action (ACCEPT/REJECT), and byte/packet counts.
  • Can be enabled at three levels: VPC (all traffic), Subnet (all ENIs in that subnet), or ENI (single interface).
  • For targeted logging (e.g., traffic between two specific subnets), enable at the subnet level - it automatically covers all current and future ENIs without per-instance management.
  • Destinations: CloudWatch Logs (near real-time analysis, metric filters, alarms), S3 (cost-effective long-term storage, Athena queries), or Kinesis Data Firehose.
  • Flow Logs do NOT capture: DNS traffic to the VPC DNS server, DHCP traffic, traffic to the instance metadata service (169.254.169.254), or traffic to/from the Amazon Time Sync Service.
  • Flow Logs cannot be modified after creation - you must delete and recreate.

5. Internet Access

  • A subnet is public if its route table has a route to an IGW (0.0.0.0/0 -> igw-xxx) AND instances have public/Elastic IPs. A subnet is private if it lacks this route.
  • NAT Gateway: Managed, placed in a public subnet with an Elastic IP. Private subnet route table needs 0.0.0.0/0 -> nat-gw-xxx. NAT Gateway does NOT have a Security Group. It is AZ-specific - for high availability, deploy one NAT Gateway per AZ with each private subnet routing to the NAT Gateway in its own AZ.
  • NAT Gateway is IPv4 only. For IPv6 outbound-only internet access (no inbound initiation from the internet), use an Egress-Only Internet Gateway. NAT is an IPv4 concept - IPv6's vast address space makes it unnecessary.
  • NAT Instance (legacy): An EC2 instance performing NAT. Must disable source/destination check. Has a Security Group. Not managed, not highly available by default. Know this exists but NAT Gateway is the recommended answer on the exam.
  • IPv6 in VPC: AWS assigns a /56 IPv6 CIDR to the VPC and /64 to subnets. All IPv6 addresses are globally unique and public - there is no "private" IPv6. Use Egress-Only IGW to allow outbound-only.

6. VPC Endpoints - AWS Service Access

  • Gateway Endpoint: For S3 and DynamoDB only. Free. Uses route table entries pointing to a prefix list. Regional - only works for buckets/tables in the same Region. Cannot be accessed from on-premises or from a peered VPC.
  • Interface Endpoint (AWS PrivateLink): For 80+ AWS services (including S3 as an alternative). Costs money (hourly + data). Creates an ENI with a private IP in your subnet. Uses DNS - not route tables. Can be accessed from on-premises via DX/VPN and from peered VPCs.
  • Gateway vs Interface - when to use which for S3:
    • From within the same VPC -> Gateway Endpoint (free, simple).
    • From on-premises or peered VPCs -> Interface Endpoint (because Gateway Endpoints are not reachable from outside the VPC).
  • VPC Endpoint Policies: Both Gateway and Interface Endpoints support resource-based policies that control which AWS principals can use the endpoint and which resources they can access (e.g., restrict to specific S3 buckets). This is an additional layer on top of IAM policies.
  • Interface Endpoint Private DNS: To make the default service hostname (e.g., ec2.eu-west-1.amazonaws.com) resolve to the endpoint's private IPs, you must enable: (1) Private DNS on the VPC endpoint, AND (2) DNS Resolution and DNS Hostnames on the VPC. Both are required.

7. Custom Service Access (PrivateLink)

  • Use PrivateLink to expose your own service to other VPCs/accounts privately (no internet, no peering, no Transit Gateway needed).
  • Architecture: Producer VPC creates a VPC Endpoint Service pointing to an NLB (Network Load Balancer). Consumer VPC creates an Interface Endpoint to connect.
  • Traffic flows over the AWS backbone, never the public internet. The consumer only sees the ENI IP - they never see the producer's VPC CIDR.
  • Supports cross-account and cross-Region access.

8. VPC Peering

  • VPC peering is non-transitive. A↔B and B↔C does NOT mean A↔C. You must create a direct peering connection for every pair that needs to communicate.
  • Works cross-account and cross-Region.
  • CIDRs must not overlap between peered VPCs.
  • You must update route tables in BOTH VPCs to route traffic to each other's CIDR via the peering connection.
  • Peering does not support edge-to-edge routing: you cannot use a peered VPC's IGW, NAT Gateway, VPN connection, or Direct Connect to access resources through it.

9. Transit Gateway (TGW)

  • Regional hub-and-spoke service. Attach VPCs, VPN connections, Direct Connect gateways, and other Transit Gateways (inter-Region peering).
  • Supports transitive routing - solves the "full mesh peering" problem at scale. If 10 VPCs are attached, they can all communicate through TGW without 45 peering connections.
  • Uses route tables for fine-grained control (e.g., isolate production VPCs from development VPCs).
  • Supports multicast.
  • Can be shared across accounts via AWS RAM (Resource Access Manager).
  • When to choose TGW vs Peering: Peering for a few VPCs with simple connectivity. TGW for many VPCs, on-premises integration, or complex routing requirements.

10. On-Premises Connectivity

  • Direct Connect (DX): Physical dedicated fiber connection between on-premises and AWS. Takes weeks/months to set up. Provides consistent bandwidth (1 Gbps, 10 Gbps, 100 Gbps), low latency, and private connectivity. NOT encrypted by default - add a VPN on top of DX for encryption.
  • Site-to-Site VPN: Encrypted IPSec tunnel over the public internet. Quick to set up (minutes). Less reliable than DX (internet-dependent). Requires a Virtual Private Gateway (or Transit Gateway) on the AWS side and a Customer Gateway on the on-premises side.
  • DX + VPN combination: For encrypted, high-bandwidth, reliable connectivity. Run a VPN connection over the Direct Connect link.
  • Direct Connect Gateway: Allows a single DX connection to access VPCs in multiple Regions.
  • VPN CloudHub: Allows multiple on-premises sites to communicate with each other through a Virtual Private Gateway using multiple VPN connections in a hub-and-spoke model.

11. On-Premises AWS Service Access

  • To access any AWS service (including S3) from on-premises, you must use an Interface Endpoint. Connect to that endpoint via Direct Connect or VPN through a Transit Gateway or Virtual Private Gateway.
  • Gateway Endpoints cannot be reached from on-premises - only Interface Endpoints can.

12. DNS Resolution (Hybrid)

  • VPC DNS: The VPC DNS server runs at the VPC base CIDR + 2 (e.g., 10.0.0.2). Enable DNS Resolution (enableDnsSupport) for instances to use it. Enable DNS Hostnames (enableDnsHostnames) for instances to get public DNS names.
  • Route 53 Private Hosted Zones: Create DNS records that are only resolvable from within associated VPCs. A private hosted zone can be associated with VPCs across accounts.
  • Route 53 Resolver Inbound Endpoint: On-premises DNS forwards queries to this endpoint -> resolves VPC private hosted zones from on-prem.
  • Route 53 Resolver Outbound Endpoint: VPC instances forward DNS queries through this endpoint -> resolves on-premises domain names from VPC. Requires forwarding rules specifying which domains go to which on-prem DNS servers.
  • You need BOTH endpoints for full bidirectional hybrid DNS resolution.

13. Network Firewall vs NACLs vs Security Groups

  • Security Groups: First line of defense. Instance/ENI-level. Stateful. Allow-only rules. Best for: controlling access to individual resources.
  • NACLs: Second line of defense. Subnet-level. Stateless. Allow and Deny rules. Best for: blocking specific IPs or CIDR ranges across an entire subnet.
  • AWS Network Firewall: Managed firewall service deployed in its own subnet. Supports deep packet inspection, intrusion prevention (IPS), domain-name filtering (allow/block traffic to specific domains), and protocol-level rules. Best for: enterprise-grade perimeter security, compliance, centralized traffic filtering across VPCs via Transit Gateway.
  • Exam decision pattern: Simple allow/deny by IP -> NACL. Per-instance access control -> Security Group. Domain filtering, IPS, deep inspection -> Network Firewall.

14. Elastic Network Interfaces (ENI), Elastic IP, Elastic Fabric Adapter

  • ENI: Virtual network card. Each instance has a primary ENI (eth0) that cannot be detached. You can attach secondary ENIs for multi-homed instances, management networks, or failover (move an ENI from one instance to another to redirect traffic).
  • Elastic IP: Static public IPv4 address. You are charged if it is NOT attached to a running instance (to discourage waste). Limited to 5 per Region by default.
  • Enhanced Networking (SR-IOV): Higher bandwidth, lower latency. Use ENA (Elastic Network Adapter) - supports up to 100 Gbps. Exam may also mention Intel VF (legacy, up to 10 Gbps).
  • Elastic Fabric Adapter (EFA): For HPC (High Performance Computing) and ML workloads. Provides OS-bypass for ultra-low latency inter-instance communication. Only works on Linux.

15. Traffic Mirroring

  • Copies actual network packets (not just metadata like Flow Logs) from an ENI to a target (another ENI or a Network Load Balancer) for deep packet inspection, content analysis, or threat monitoring.
  • Use when Flow Logs aren't enough - when you need to see payload data, not just headers.
